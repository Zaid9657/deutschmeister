## 1. The one decision that shapes everything: unit order

Two registries key the A2.1 units differently.

| `lanes/ga2.json` `openQuestions` (curriculum mapping note) | the plan's order (it counts ga2.sp3 in „U2, U7, U12") | — |

**Decision: the plan's order.** The spine is the only one of the three whose unit numbers are data that a hard gate reads
(GRM-02 blocks a unit that does not list the spine's intro point as new, and the spine owner says the curriculum agents
„must not move a grammar point against this file"). The can-do registry has no unit field, so its row table can be
re-keyed without touching a registry: each blueprint row's **core set moves with its topic** to the plan unit that
carries that topic. No can-do id was invented, renamed or reworded, and every id stays core in exactly one unit of its own
half-level.

Consequences for the other readers of the blueprint order:

- The SCHEMA §15 fixture (`content/course-v2/fixtures/a2.1-u07.json`, „Am Telefon im Job") keeps its own fixture
  registries and is unaffected. The live phone unit is **a2.1-u08**; it carries exactly the fixture's four can-dos.
- BLUEPRINT §2.8's A2.1 table (row order, and its „Hier und dort" row 12) no longer matches the course. Its owner should
  re-key the A2.1 rows to this order; `cando-a2.md` §3/§8.2 unit numbers should be re-keyed by the can-do owner.
